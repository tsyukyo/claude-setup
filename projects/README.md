# Claude Code Projects 立ち上げガイド

Claude Code Projects（claude.ai/code・デスクトップアプリの Code タブ・モバイルアプリ）で新しいプロジェクトを作るときの手順と、各入力欄に書く内容です。
公式ドキュメント: <https://code.claude.com/docs/en/claude-projects>

## 手順の全体像

1. [一度だけ行う準備](#一度だけ行う準備)（初回のみ）
2. [New project ダイアログ](#new-project-ダイアログ)で名前・取り組むこと・コンテキストを入力
3. [4 つの基本設定](#4-つの基本設定)（取り組むこと・コーディネーターモデル・スレッドモデル・スレッドのエフォート）を決める
4. [その他の Project settings](#その他の-project-settings)（プロジェクト指示・環境・プラグイン）
5. [最初のバッチ](#最初のバッチ)で小さく試してから本格的に任せる

## Projects で読み込まれるもの・読み込まれないもの

この構成は次の仕様を前提にしています。

| リポジトリ内のもの | Projects のクラウドスレッド | この構成での対応 |
|---|---|---|
| ルートの `CLAUDE.md`・`.claude/CLAUDE.md`・`.claude/rules/` | 読み込まれる | 委任ルールは `CLAUDE.md` に置く |
| `.claude/agents/`・`.claude/skills/` | **読み込まれない** | `dev-team` プラグインにまとめ、Project settings → Plugins で追加 |
| `.claude/settings.json`（model・権限・hooks・env・プラグイン） | **適用されない** | モデルとエフォートは Project settings → General で指定。権限は auto mode とスレッド内の承認 |
| 手元の `~/.claude/CLAUDE.md` | 読み込まれない | クラウド環境の Setup script で書き出す（`cloud/setup-script.sh`） |
| claude.ai の個人設定・コネクタ | 使われる | `claude-ai/personal-preferences.md` を貼り付け |

> **注意: Projects ではリポジトリの deny ルールが効きません。** `.env` の読み取り禁止や強制 push の禁止は、プロジェクト指示の文言と auto mode・スレッド内の承認だけが頼りです。秘密情報はリポジトリに置かず、クラウド環境のネットワークシークレットに置いてください。

## 一度だけ行う準備

1. **プラン**: Pro / Max / Ultra で、サイドバーに **Projects**（または **More** の中）が表示されていること。
2. **GitHub**: 対象リポジトリに Claude GitHub App をインストールし、接続した GitHub アカウントに push 権限があること（`/web-setup` のトークンだけでは不足）。
3. **プラグイン**: claude.ai の **Customize → Plugins → Add** から、公開リポジトリ `tsyukyo/claude-setup` をマーケットプレイスとして追加し、`dev-team` をインストールする。
4. **claude.ai 個人設定**: `claude-ai/personal-preferences.md` のコードブロックを貼り付ける。
5. **クラウド環境**: claude.ai/code の環境設定で自分専用の環境を作り、Setup script に `cloud/setup-script.sh` の中身を貼り付ける。必要なら許可ドメイン・ネットワークシークレットもここで設定する（秘密情報は環境変数ではなくネットワークシークレットに置く）。

## New project ダイアログ

| 欄 | 書く内容 | 例 |
|---|---|---|
| **Name**（必須） | 継続的に追加していく 1 つの作業の流れの名前 | `kakeibo-web MVP` |
| **何に取り組みますか？**（Goal・任意） | 下の「[1. 何に取り組みますか？](#1-何に取り組みますか)」を参照 | `kakeibo-web の MVP を 11 月末までに Workers へ公開する` |
| **Context**（任意） | ほぼすべてのタスクで触るリポジトリ 1〜2 個と、スレッドに読ませたい資料（仕様書・デザイン・API 仕様など） | `tsyukyo/kakeibo-web`、`docs/要件定義.pdf` |

- リポジトリは「ほとんどのタスクで使うもの」だけを追加し、他はプロジェクト指示に名前を書いておく（スレッドが必要なときに自分で追加する）。
- アップロードしたファイルはコピーなので、手元で更新したら Library タブから再アップロード（Replace）する。

## 4 つの基本設定

ダイアログで入力した後も、**Project settings → General** でいつでも変更できます。新しいプロジェクトの既定は「**すべて Opus、スレッドは high エフォート**」で、公式ドキュメントでも「プランの使用量を最も速く消費する」とされています。そのため、作成直後に必ず見直してください。

### 推奨値（早見表）

| 設定 | 推奨値 | 既定値 |
|---|---|---|
| 何に取り組みますか？ | 成果と完了条件を 1 行で（例は下記） | 空欄 |
| コーディネーターモデル | **Opus 5.5**（エフォート欄があれば **low**） | Opus 5.5 / low |
| スレッドモデル | **Sonnet 5.5** | Opus 5.5 |
| スレッドのエフォート | **medium**（バグ修正・既存コードの改修が中心なら **high**） | high |

### 1. 何に取り組みますか？

コーディネーターは、ここに書いた成果に向けてタスクを分割し、スレッドを立て、進捗を判断します。ここが曖昧だと、スレッドの分け方や「完了」の判断がぶれます。

**書き方のルール**

- **1 行・1 つの成果**にする。作業の手順やタスクの一覧ではなく、目指す状態を書く。
- **完了したと判断できる条件**を入れる（数値・公開・テスト合格など）。
- 必要なら**期限や範囲の制約**を 1 つだけ添える（例: 「既存 API を変えずに」）。
- 細かいルール（ブランチ、PR、検証方法）はここではなく**プロジェクト指示**に書く。

**型**: `<対象> を <完了条件> の状態にする（<期限・制約>）`

| 良い例 | 悪い例（理由） |
|---|---|
| `kakeibo-web の MVP（記録・一覧・月次集計）を 11 月末までに Workers へ公開する` | `家計簿アプリを作る`（完了条件がない） |
| `payments-api の p95 レイテンシを 200 ms 以下に保つ` | `パフォーマンス改善`（測れない） |
| `全サービスを新しい ESLint 設定に移行し、CI を緑にする` | `ESLint を入れて、テストを書いて、README も直す`（タスク一覧になっている） |
| `ORM を Prisma から Drizzle に移行する（API の互換性を保つ）` | `いろいろリファクタリング`（範囲がない） |

進め方が決まっていない探索的なプロジェクトなら、空欄で始めて、方向が固まってから書き足してもかまいません。

### 2. コーディネーターモデル → Opus 5.5

コーディネーターは、プロジェクトの会話でタスクを振り分け、スレッドを作って管理し、スレッドから戻ってきた報告を読んで次の手を決めます。

- **Opus 5.5 を推奨**: 「どう分割するか」「どのスレッドを優先するか」「報告が本当に完了しているか」は、このプロジェクトでいちばん大きな判断です。この構成で Opus を充てる「重大判断・サインオフ」にあたります。
- **消費は小さい**: コーディネーターが読むのはスレッドの報告だけで、スレッドの作業の全ステップは見ません。直近のメッセージ・スレッド・プロジェクトメモリをもとに動くので、会話の全履歴を抱え込みません。
- **エフォートは low のまま**: 欄が表示される場合は既定の low のままにします。振り分けの判断に深い推論は不要で、low のほうが応答も速くなります。
- **使用量を抑えたい場合**: Pro プランで上限に早く達するようなら、Sonnet 5.5 に下げます。

### 3. スレッドモデル → Sonnet 5.5

スレッドは、実装・修正・テスト・PR 作成を行う実働部隊で、使用量の大半を占めます。

- **Sonnet 5.5 を推奨**: 公式の説明は「日常のコーディング作業向け」です。この構成の「Sonnet が実装する」にあたります。
- **調査と監査は自動的に Haiku、判断は Opus になる**: スレッドが呼び出す `dev-team` のサブエージェントは、プラグイン側でモデルを指定しています（search / grep / audit は Haiku 5.5、advisor は Opus 5.5）。スレッドモデルを Sonnet にしても、この使い分けは変わりません。
- **タスク単位で上げ下げできる**: 難しい設計や原因不明の障害だけを任せるときは「このタスクは Opus で」、定型作業なら「このタスクは Haiku で」とタスクの依頼文に書きます。実行中のスレッドは、そのスレッドのモデル選択で切り替えます。
- **Opus を既定にしてよい場合**: 大規模なアーキテクチャ変更や、セキュリティ監査が中心のプロジェクトで、使用量に余裕があるときだけにします。

### 4. スレッドのエフォート → medium（必要なら high）

エフォートは、1 ターンでどれだけ考え、どれだけ検証するかの設定です。高いほど端のケースまで確かめて自分で判断しますが、思考トークンの消費が増えます（思考トークンは表示が折りたたまれていても課金対象です）。

| レベル | 公式の推奨用途 | このプロジェクトでの使いどころ |
|---|---|---|
| low | 短いやり取り、ブレスト、リネームなどの小さな変更 | スレッドの既定には使わない |
| **medium** | 範囲が明確な日常のエンジニアリング（新機能の実装など）。Sonnet 5.5 / Opus 5.5 の既定値 | **新規開発・機能追加が中心のプロジェクトの既定値** |
| **high** | 検証が重要な作業、端のケースが多い作業（既存コードのバグ修正など） | **バグ修正・既存コードの改修・移行が中心なら既定値にする** |
| xhigh | さらに深い推論（消費も多い） | 難しい不具合のスレッドだけ、依頼時に指定する |
| max | 人が付きっきりにならずに難問を解かせたい場合（脆弱性の発見など）。収穫が逓減しやすい | 既定にしない。必要なタスクだけ、試してから使う |

- 迷ったら **medium** で始め、最初のスレッドの結果を見て決めます。検証が甘い、端のケースを見落とすといった問題があれば high に上げます。
- この構成では、検証の大部分を audit（Haiku）と advisor（Opus）が受け持ちます。そのため、スレッド自体のエフォートを上げなくても品質を確保しやすくなっています。

## その他の Project settings

| 設定 | 推奨値 | 理由 |
|---|---|---|
| Memory → **Project instructions** | `projects/project-instructions.md` を記入して貼り付け | すべての新規スレッドとコーディネーターに渡される |
| Environment → **Repositories** | ダイアログで追加したもの | — |
| Environment → **Cloud environment** | 準備 5 で作った環境 | Setup script で `~/.claude/CLAUDE.md` を配置するため |
| **Plugins** | `dev-team` | search / grep / audit / advisor と `/dev-team:init` をスレッドで使うため |

設定の変更は**新しく始まるスレッド**にだけ反映されます。実行中のスレッドには反映されません。

## 最初のバッチ

公式の推奨どおり、最初は小さく試し、スレッドの報告のされ方を確かめてから本格的に任せます。

1. 実際の作業のうち小さなものを 1 つだけ送り、終わったらスレッドを開いて、報告の内容とブランチで何をしたかを確認する。
2. 思い込みで進めていたり、必要なものに届かず止まっていたりしたら、原因をプロジェクト指示か環境で直してから次を送る。
3. 最初のうちは「スレッドを始める前に提案して、私の go を待って」「同時に動かすのは 2 つまで」と伝え、思いどおりに戻ってくるようになったら外す。
4. Project settings → **Usage** でモデル別の消費を確認し、Haiku（search / grep / audit）と Opus（advisor）が実際に使われているかを一度確かめる。

新規リポジトリ（CLAUDE.md がまだない）の場合の最初のメッセージ:

```text
<owner/repo> に /dev-team:init を実行して dev-team 構成を導入し、draft PR を作成してください。
完了したら、リポジトリの現状と目標までのタスク分割案を提案し、私の go を待ってからスレッドを開始してください。
同時に動かすスレッドは最大 2 つにしてください。
```

既存リポジトリの場合の最初のメッセージ:

```text
まず dev-team:search でリポジトリ全体を把握し、何も変更せずに現状の課題と次のタスク案を提案してください。
スレッドは私の go を待ってから開始し、同時に動かすのは最大 2 つにしてください。
```

## 運用のコツ

- スレッドの作業を修正させたら「この修正を覚えておいて」と伝える。プロジェクトメモリに保存され、以後のスレッドが最初から従う。
- 必ず守らせたい運用ルール（同時スレッド数、PR を作るタイミングなど）は、会話で伝えるだけでなくプロジェクト指示に書く。会話での指示は「好み」として扱われ、強制ではない。
- 小さな質問は「スレッドを立てずにここで答えて」と伝えると使用量を節約できる。
- 1 時間以上放置した大きなスレッドに追加の依頼をすると、会話全体を読み直すので消費が増える。新しい作業は新しいスレッドで始めてもらう。
