# プロジェクト指示テンプレート

Claude Code Projects の **Project settings → Memory → Project instructions** に、下のコードブロックの中身を貼り付けます（上限 16,000 文字）。
`<...>` の部分をプロジェクトごとに書き換えてください。リポジトリ固有のルール（ビルドコマンドなど）は各リポジトリの `CLAUDE.md` に書き、ここには書きません。

```text
# 目的と範囲
<「何に取り組みますか？」の 1 行を補足する。背景・含むもの・含まないものを書く。例:
個人用の家計簿 Web アプリ kakeibo-web の MVP。含む: 支出の記録・一覧・月次集計、Cloudflare Workers への公開。含まない: 認証の多要素化、ネイティブアプリ>

# スレッドの立て方
- スレッドは 1 つの PR にまとまる大きさで立てる。依存関係のあるタスクは順番に、独立したタスクは並列にする。
- スレッドの既定モデル（Sonnet）で足りないタスク（アーキテクチャの決定、原因不明の障害、セキュリティに関わる変更）は Opus で、定型作業（文言修正、依存関係の更新、ドキュメント整備）は Haiku でスレッドを立ててよい。
- スレッドの報告を受けたら、完了条件を満たしているか（audit の PASS と検証結果の記載）を確認してから完了扱いにする。

# 作業場所
- 主リポジトリ: <owner/repo>（基準ブランチ: main）
- 関連リポジトリ（必要なスレッドだけが追加する）: <owner/repo-api など。なければ削除>
- スレッドごとに作業ブランチを切り、draft PR を 1 つ作成する。PR タイトルは「<種別>: <要約>」（種別: feat / fix / chore / docs / refactor / test）。

# 進め方
- 回答・報告・PR 本文・コメントは日本語で書く。
- 通常の技術判断は自律的に行い、仮定は明記して進める。計画だけで止めず、検証まで完了させる。
- 各リポジトリの CLAUDE.md に従う。CLAUDE.md がないリポジトリでは、最初に /dev-team:init の実行を提案する。
- リポジトリ検索とテスト実行は Haiku のサブエージェント（dev-team:search / dev-team:grep / dev-team:audit）に委任し、スレッドのコンテキストを小さく保つ。プラグインが使えない場合は Explore などを model: haiku で代用する。
- 重大な判断（スキーマ、認証・認可、課金、公開 API、データ削除、セキュリティ設定）は dev-team:advisor（Opus）に相談し、PR 前にサインオフを得る。
- 長いタスクでは、区切りごとに作業ブランチへコミットして push してよい（サンドボックス再開時に未コミット変更が失われるため）。PR を作成するのは dev-team:audit が PASS した後にする。

# 完了の条件
- 作業ブランチにコミットしたうえで dev-team:audit を実行し、PASS を得る。
- 最終メッセージに、実行したテスト・型チェック・Lint・ビルドのコマンドと結果の要約行を貼る。
- 検証できなかった項目は「未検証」と理由を書く。テストやチェックを弱めて成功を装わない。

# 不足があるとき
- リポジトリ、秘密情報、API、コネクタなど必要なものに到達できない場合は、最初のメッセージで何が足りないかを具体的に書いて止まる。代用・モック・推測で進めない。

# 事前に確認が必要なこと
- main へのマージ、強制 push、履歴の書き換え
- CI 設定・本番環境・課金設定の変更、本番データの削除、破壊的マイグレーション
- 新しい有料サービスや依存関係の大幅な追加

# 報告の形式
1. 実施内容と主な変更ファイル
2. 検証の内容と結果
3. ブランチ・コミット ID・PR の URL
4. 未解決事項・未検証項目・ユーザーに必要な対応
```
